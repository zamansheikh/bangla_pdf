# CURRENT_STATE — how `bangla_pdf` 1.0.6 actually works

Status: Phase 1 audit. Describes the shipped 1.0.6 code with **no changes applied**.
All claims here were produced by running the 1.0.6 code, parsing the embedded font,
and parsing a PDF generated by the unmodified package. Reproduction commands are at
the bottom.

---

## 1. The headline fact

**`bangla_pdf` 1.0.6 is not a Unicode pipeline. It is a Unicode → Bijoy-ANSI transcoder
paired with a legacy 8-bit font.**

The bundled font is not the Unicode Kalpurush. Parsing
[default_font_data.dart](../lib/src/core/default_font_data.dart):

| property | value |
|---|---|
| `name[1]` family | `Kalpurush ANSI` |
| `name[6]` PostScript | `KalpurushANSI` |
| glyph count | 231 |
| `cmap` (3,1) coverage | 95 ASCII + 96 Latin-1 supplement codepoints |
| **Bengali codepoints U+0980–U+09FF in `cmap`** | **0** |
| `GSUB` table | **absent** |
| `GPOS` table | **absent** |

So the font cannot render a Bengali codepoint at all, and has no OpenType layout data.
Every conjunct it can draw must already exist as one of its 231 precomposed glyphs,
selected by an 8-bit code. That is what `BanglaUnicodeMapper` produces.

The consequence is that a PDF produced by 1.0.6 contains **no Bengali text**. Its
`/ToUnicode` CMap maps to Latin-1. Copy/paste, `pdftotext`, search, screen readers and
accessibility tooling all return ANSI mojibake. See §6 for the measured proof.

## 2. File inventory

`lib/bangla_pdf.dart` is a single `library` assembled from seven `part` files. There is
no `src/` privacy boundary — everything in every part file is public API surface once
exported, and all of it currently is.

## 3. The exact code path from `Text()` to the PDF content stream

```
Text(text, …)                              fx_widgets.dart:19
  └─ build() → AutoText(text, …)           fx_widgets.dart:37-54
       └─ build() → pw.RichText(           fx_widgets.dart:266-287
            text: pw.TextSpan(
              children: FixingUtils.getAutoLocalizedSpans(…)))
                 │
                 ├─ RegExp(r'[ঀ-৿।॥]+ *')   fixing_utils.dart:39
                 │     splits the string into Bangla runs and non-Bangla runs.
                 │     NOTE the trailing ` *` — a Bangla run swallows the spaces
                 │     that follow it. This matters; see §5.1.
                 │
                 ├─ non-Bangla run → pw.TextSpan(style: generalFont ?? <none>)
                 │     with no font set this resolves to Helvetica (base-14),
                 │     which is Latin-1 only. Emoji and CJK silently drop.
                 │
                 └─ Bangla run → match.group(0)!.fix                fixing_utils.dart:78
                       └─ BanglaTextExtension.fix                   helper/font_manager.dart:7
                            └─ BanglaUnicodeMapper.encodeANSI       unicode_mapper.dart:12
                                 └─ _fixFont                        unicode_mapper.dart:16
                       → pw.TextSpan(text: <ANSI bytes>,
                                     style: font = banglaFont
                                            ?? banglaStyle.font
                                            ?? BanglaFontManager().defaultFont)
                                                                    fixing_utils.dart:50-63
                 ↓
            pw.RichText lays out and calls PdfTtfFont.putText
                 ↓
            pdf 3.13.0 obj/ttffont.dart:170 putText
                 – sfnt version is 0x00010000 so `font.unicode` is true,
                   therefore a Type0 / Identity-H CID font is built
                 – each **rune of the ANSI string** is appended to
                   `unicodeCMap.cmap` and its *index* is emitted as the CID
                 – `/ToUnicode` therefore maps CID → the ANSI Latin-1 rune
```

`Header`, `Paragraph`, `BulletList` all delegate to `AutoText`.
`Table` and `RichText` call `FixingUtils.getAutoLocalizedSpans` directly. So there is
exactly **one** transcoding chokepoint — `getAutoLocalizedSpans` — and one transform,
`String.fix`. That is good news for Phase 3: the whole widget layer can be re-routed by
replacing the body of `getAutoLocalizedSpans`.

## 4. What `_fixFont` does, stage by stage

`BanglaUnicodeMapper.encodeANSI(String)` → `_fixFont` ([unicode_mapper.dart:16](../lib/src/utils/unicode_mapper.dart#L16)):

### Stage 1 — pre-normalisation (lines 17–21)
| replacement | effect |
|---|---|
| `"য়" → "য়"` | NFD ya+nukta (U+09AF U+09BC) → precomposed U+09DF |
| `U+09A1 U+09BC → U+09DC` | NFD dda+nukta → precomposed rra (ড়) |
| `U+09A2 U+09BC → U+09DD` | NFD ddha+nukta → precomposed rha (ঢ়) |
| `U+200D → U+200C` | **every ZWJ is rewritten to ZWNJ** |

The ZWJ→ZWNJ rewrite is the only ZWJ handling in the package. It destroys the
`র‍্য` (ra+ZWJ+virama+ya) vs `র্য` (reph+ya) distinction *before* the reorder pass runs;
the two then diverge only by accident of the reorder code. There is no NFC/NFD
normalisation beyond the three nukta pairs above — e.g. `ো` given as `ে`+`া` is patched
by a separate literal replace at line 42, not by a normaliser.

### Stage 2 — line split (lines 23–28)
The string is split on `\n`, each line is passed to `_fixFontInner`, and `\n` is
re-appended.

### Stage 3 — `_fixFontInner` (lines 41–52)
1. Literal replace of decomposed `ো` and `ৌ` with their precomposed forms.
2. `_rearrangeUnicodeStr` — the reorder engine (§5).
3. `_conversionMap.forEach { replaceAll(key, value) }` — 220 sequential
   `String.replaceAll` calls in **map insertion order**.

### Stage 4 — post-processing (lines 30–38)
**Every `\n` inserted in stage 2 is stripped again** (`result.replaceAll("\n", "")`),
so `.fix` collapses multi-line input to a single line. Then every U+200C is deleted.

Because `getAutoLocalizedSpans`' regex never matches across a newline, this newline
destruction is invisible through the widgets — but `.fix` is public API and does lose
line breaks when called directly.

## 5. Every reorder rule, in full

`_rearrangeUnicodeStr` ([unicode_mapper.dart:54](../lib/src/utils/unicode_mapper.dart#L54))
is a single forward scan with a `barrier` index. It implements exactly **two** rules.

### Rule 1 — pre-base vowel reordering (lines 63–81)
Trigger: current char is one of `ি` `ৈ` `ে` (`_isBanglaPreKar`, line 124).
`ো` and `ৌ` are *not* in that set — they were already decomposed-then-recomposed and are
handled by `_conversionMap` splitting them into `‡`+`v` / `‡`+`Š`.

Walk left over the consonant cluster: while `text[i-j]` is a consonant, if `text[i-j-1]`
is a virama then `j += 2` (skip one more consonant+virama pair), else stop. Then move the
vowel sign to position `i-j`, i.e. in front of the whole cluster. `barrier` is set to
`i+1` to stop a later rule crossing it.

`_isBanglaBanjonborno` (line 128) is the consonant test. It is **not** the Bengali
consonant set: it omits `ড়` `ঢ়` and includes `ং` `ঃ` `ঁ` `ৎ`, which are not consonants.
That mis-classification is why the left-walk stops in the wrong place for words
containing `ড়`/`ঢ়` inside a cluster.

### Rule 2 — reph reordering (lines 83–112)
Trigger: `text[i]` is virama, `text[i-1] == 'র'`, and `text[i-2]` is not a virama.
Walk right over consonant+virama pairs (`j += 2`) until either a consonant followed by a
pre-base vowel is found (`foundPreKar = 1`) or the chain ends. Then rebuild the string as

```
prefix | optional pre-base vowel | the consonant chain | 'র' | virama | rest
```

so the `র`+virama pair lands *after* the cluster it governs, where `_conversionMap`
turns `র্` into `©` — the ANSI post-base reph glyph.

### That is the entire shaping model
There is no half-form logic, no below-base (`blwf`) logic, no post-base (`pstf`) logic,
no `akhn`, no `vatu`, no mark positioning, no cluster model. Everything else — every
conjunct, both phalas, khanda-ta, nukta forms, digits — is a flat string substitution
from `_conversionMap`.

### 5.1 Defect: unguarded indices → `RangeError` on reph
Rule 2 reads `processedText[i - 2]` with no lower bound and
`processedText[i + j + 1]` with no upper bound. Rule 1 reads `processedText[i - j]`
before its own `if (i - j < 0) break`. Measured result (`tool/baseline/reph_crash_probe.dart`):

```
CRASH  কর্ম       ধর্ম       বর্ষ       পূর্ব       শর্ত       র্ক       আমার কর্ম
ok     কর্ম<space>   কর্ম।     কর্মচারী   কার্যক্রম   নির্বাচন    দুর্গা
```

A reph word crashes **iff it ends the Bangla run**. It survives when followed by a space
or a danda, because the regex's trailing ` *` (or the danda being inside the Bangla class)
lengthens the string enough for the out-of-range read to land in bounds. This is an
uncaught exception thrown inside `pw.Widget.build`, so it aborts the whole
`pdf.save()`. `ি` or `ে` alone, and a leading `্র`, crash the same way.

This is a live production defect in 1.0.6, not a cosmetic one. I would like to ship it as
a `1.0.7` patch before the rest of this work lands — see the Phase 1 summary.

### 5.2 Defect: `_conversionMap` is order-dependent and has 7 dead entries
Substitution is `replaceAll` in insertion order with no longest-match rule, so any key
that contains an earlier key can never fire:

| dead entry | consumed first by |
|---|---|
| `ঙ্ক্ষ` | `ক্ষ` |
| `চ্ছ্ব` | `চ্ছ` |
| `ত্ত্ব` | `ত্ত` |
| `ন্দ্ব` | `দ্ব` |
| `ম্ভ্র` | `ভ্র` |
| `ষ্ক্র` | `ক্র` |
| `স্তু` | `স্ত` |

### 5.3 Defect: unmapped conjuncts degrade to a visible hasanta
`"্": "&"` is the last-resort rule. `&` (U+0026) is mapped in Kalpurush ANSI to a
**visible hasanta glyph**, so any conjunct absent from the table renders as
base + ্ + base rather than a ligature. Rasterised with `hb-view` (see BASELINE.md),
`ক্ষ্ম ঙ্ক্ষ ত্ত্ব চ্ছ্ব ম্ভ্র` come out as `ক্ষ্‌ম ঙ্‌ক্ষ ত্ত্‌ব চ্ছ্‌ব ম্‌ভ্র`.

### 5.4 Defect: characters with no ANSI mapping fall through as raw Unicode
`ৰ` (U+09F0), `ৱ` (U+09F1) and `॥` (U+0965) are in the Bangla regex but not in
`_conversionMap`, so they reach the ANSI font as Bengali codepoints, which it has no
`cmap` entry for → notdef.

## 6. Measured end-to-end evidence

A PDF was generated with the **unmodified** 1.0.6 package (three `Text` widgets), then
parsed. Its single `/ToUnicode` CMap contains 26 `bfchar` entries, mapping to:

```
￿ A v g i ‡ m b e s j w Z q f | ¶ & O Ë ” Q å ` k
```

Reconstructing the page text through that CMap — i.e. exactly what a viewer puts on the
clipboard:

```
Avgvi ‡mvbvi evsjv , Avwg ‡Zvgvq fv‡jvevwm| ¶&g O&¶ Ë&e ”Q&e g&å Hello evsjv‡`k world!
```

Expected: `আমার সোনার বাংলা, আমি তোমায় ভালোবাসি। ক্ষ্ম ঙ্ক্ষ ত্ত্ব চ্ছ্ব ম্ভ্র Hello বাংলাদেশ world!`

Not one Bengali codepoint survives.

Separately, non-Bangla runs get no font at all, so `package:pdf` falls back to base-14
Helvetica (Latin-1 only). Generating `Text('Hi 🐒 বাংলা!')` logs

```
Helvetica has no Unicode support …          (assert-only, fires whenever a base-14 font is built)
Unable to find a font to draw "🐒" (U+1f412) try to provide a TextStyle.fontFallback
```

and emits `package:pdf`'s crossed-box placeholder path into the content stream in place
of the emoji. The README's emoji example
(`'Hello 🐒💁👌🎍😍🦊👨বাংলাদেশ world!'`) therefore renders as seven crossed boxes.
That is a README overclaim, not a code regression.

## 7. Public API surface that must not break

Everything below is reachable by an existing 1.x user and must keep working unchanged.

| symbol | notes for Phase 3 |
|---|---|
| `Text`, `AutoText`, `RichText`, `TextSpan`, `Header`, `Paragraph`, `BulletList`, `Table` | all constructor parameters must survive |
| `RichTextItem` | dead but exported — keep, do not remove |
| `BanglaFontManager()`, `.defaultFont`, `BanglaFontManager.isBanglaText` | `defaultFont` currently returns an **ANSI** font |
| `FixingUtils.getAutoLocalizedSpans`, `.fixTableData`, `.loadImage` | `getAutoLocalizedSpans` returns `List<pw.TextSpan>` — signature is load-bearing |
| `String.isBanglaText`, `String.fix` | `.fix` returns ANSI bytes; users may be feeding these into their own `pw.Text` |

### The hard compatibility constraint
`banglaFont:` and `banglaStyle.font` accept a user-supplied `pw.Font`. Because the text
handed to it is **already transcoded to ANSI**, that font must itself be a Bijoy/ANSI
font. Users who pass SutonnyMJ or Kalpurush-ANSI work today; users who pass a Unicode
font (Noto Sans Bengali) get garbage today. Any Phase 3 pipeline that emits real Unicode
will invert that: it will need Unicode fonts and will break the ANSI-font users.

**This is the one place where "no behaviour change" and "correct Bangla" are in direct
conflict, and it is the reason the ADR proposes a mode switch that defaults to `legacy`
for the 1.x line.** It is flagged for your decision in the Phase 1 summary.
